# 🛡️ Empirical Verification & Evidence Hierarchy Standard

## 1. The Core Problem: LLM Cognitive Pathology

Large Language Models exhibit three pervasive cognitive pathologies when evaluating their own work:
1. **Self-Aggrandizement & Sycophancy:** Using empty superlatives (*"perfectly optimized"*, *"extremely clean"*, *"flawless architecture"*) instead of concrete technical evidence.
2. **Happy-Path Confirmation Bias:** Evaluating code solely against trivial success scenarios ($1+1=2$) while ignoring edge cases, null boundaries, and concurrent race conditions.
3. **Hallucinatory Completion:** Declaring a task "complete" simply because code generation finished, without compiling, executing tests, or inspecting diffs.

In the AgentOption framework, **an agent's self-opinion has zero epistemic weight**. All claims must be anchored in external, reproducible, machine-generated proof.

---

## 2. The 5-Level Proof Hierarchy (L0–L4)

Every technical claim, diagnosis, and completion assertion is strictly categorized by evidence level:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       THE 5-LEVEL PROOF HIERARCHY                           │
├────┬──────────────────────────────────┬──────────────────────┬──────────────┤
│ L4 │ Runtime Telemetry & Stress Load  │ Benchmark, Profiler  │ HIGH PERF    │
│ L3 │ Empirical Automated Test Suite   │ Red-to-Green Runner  │ MINIMUM BAR  │
│ L2 │ Compiler & Linter Gate           │ Exit Code 0, Types   │ GATEWAY ONLY │
├────┴──────────────────────────────────┴──────────────────────┴──────────────┤
│ ⛔ REJECTED EVIDENCE TIERS (NEVER PERMITTED AS PROOF OF COMPLETION)        │
├────┬──────────────────────────────────┬──────────────────────┬──────────────┤
│ L1 │ Static Visual Inspection         │ "Looks correct"      │ INSUFFICIENT │
│ L0 │ Unsubstantiated Assertion        │ "I believe it works" │ FORBIDDEN    │
└────┴──────────────────────────────────┴──────────────────────┴──────────────┘
```

### Level 0: Unsubstantiated Assertion (Strictly Forbidden)
- *Definition:* Textual claims generated by the LLM without external reference (e.g., *"This fix resolves the memory leak"*).
- *Policy:* **Instant rejection**. The agent must never close a task at Level 0.

### Level 1: Static Visual Inspection (Insufficient)
- *Definition:* The agent reads its own diff or source files and assumes correctness because the logic seems sound.
- *Policy:* **Insufficient for verification**. Code that looks elegant frequently contains subtle runtime bugs (type mismatches, off-by-one errors, missing await keywords).

### Level 2: Compiler & Linter Gate (Gateway Baseline)
- *Definition:* The source compiles cleanly with zero warnings (`-Werror`, `/warnaserror`) and passes static type-checking (`tsc`, `mypy`).
- *Policy:* **Necessary but not sufficient**. Compiling proves syntactic and type validity, but provides zero guarantee of business correctness.

### Level 3: Empirical Automated Tests (Minimum Completion Threshold)
- *Definition:* An automated test runner executes and reports passing results with explicit assertion counts:
  - Reproduction test proved failure before the change (Red).
  - Test passed cleanly after the change (Green).
  - Regression suite passes without breaks.
- *Policy:* **The mandatory minimum bar** for closing any bugfix or feature task.

### Level 4: Runtime Telemetry & Stress Probing (High-Performance Threshold)
- *Definition:* Empirical metrics captured under live or synthetic stress:
  - Benchmark runners reporting p50/p95 latency and heap allocation deltas.
  - Concurrency harnesses detecting zero race conditions under multi-threaded load.
  - Memory profilers proving zero uncollected allocations after repeated iterations.
- *Policy:* **Mandatory for all performance optimization and concurrency tasks.**

## 3. The Adjective Ban (Language Discipline)

Agents are strictly forbidden from evaluating their own solutions using emotional, decorative, or unverified adjectives:

| ❌ Forbidden Decorative Language | ✅ Mandatory Empirical Replacement |
| :--- | :--- |
| *"The code is now extremely clean and optimal."* | *"Refactored into 3 cohesive partials; cyclomatic complexity reduced from 14 to 4."* |
| *"Performance is blazing fast."* | *"Latency dropped from 42ms to 18ms (p95, N=100 iterations)."* |
| *"Bug has been completely fixed."* | *"Reproduction test `Test_ConcurrentWrite_NoDeadlock` passed 50/50 consecutive runs."* |
| *"Memory usage is negligible."* | *"Allocations reduced from 8.4MB to 1.1MB per transaction; zero gen-2 GC collections."* |
| *"Architecture is flawless."* | *"Conforms to `standards/universal/multi-objective-refactoring.md` with zero broken contracts."* |

## 4. Adversarial Cross-Examination (The Inquisitor Check)

Before presenting any completed task to the user, the agent must execute a mandatory **Adversarial Cross-Examination**:

```
                              ┌──────────────────────────────┐
                              │  ADVERSARIAL INQUISITOR GATE │
                              └──────────────┬───────────────┘
                                             │
               ┌─────────────────────────────┼─────────────────────────────┐
               ▼                             ▼                             ▼
    [1. Failure Inversion]         [2. Negative Testing]        [3. Third-Party Witness]
    "Under what production         "Did I deliberately attempt  "What machine-generated
    conditions will this code      to BREAK this code with      output independently
    deadlock or crash?"            malformed payloads?"         proves execution?"
```

1. **Failure Inversion:** Actively hypothesize at least one edge case that could trigger a failure (e.g., disconnected network, unexpected null in DB column, unhandled concurrent cancellation).
2. **Negative Testing:** Ensure at least one test case validates graceful degradation when invalid inputs, timeouts, or unauthorized tokens are supplied.
3. **Third-Party Witness:** Cite the exact terminal command, line numbers, exit code (`0`), and passing test count that proves the machine verified the logic.

## 5. Surrogate Equivalence Verification

When physical production environments, live databases, or embedded target hardware cannot be accessed directly:
1. **In-Memory Harness:** Build a mock/in-memory reproduction harness matching the production boundary (e.g., `SqliteConnection(":memory:")` or simulated virtual CAN bus).
2. **AST & Disassembly Proof:** Inspect compiler AST, IL, or assembly output to prove zero-allocation contracts (e.g., verifying `struct` is passed by `in` reference without boxing).
3. **Formal Branch Mapping:** Construct a side-by-side truth table verifying that every branch in the legacy code has a strict 1-to-1 equivalence in the new implementation.
